Blockies / Concepts

The runtime

Everything that changes happens inside a transaction. A transaction either commits completely or changes nothing.

Running example

A presenter presses the dashboard button. One transaction carries the click through the button's reducer, the counter's reducer, the gauge's compute, and the commit. This page follows that click.

The pipeline

The analogy is a stage play. Rehearsal happens in private; the audience sees nothing until the curtain goes up. If something goes wrong in rehearsal, the performance is cancelled and the previous night's set is still standing. A transaction is the rehearsal plus the curtain; a generation is the performance the audience sees.

Staged versus committed

Staging means the transaction works on a private copy. Reducers and steps see the latest staged values; nobody outside sees anything until the commit.

A generation is one committed snapshot. Renderers read generations, never half-finished work, so a screen can never show a vote count from before the chart was recalculated.

Why one transaction

If a vote updated the count in one step and the chart in another, a viewer could see the two disagree for a frame. One commit, one picture.

Determinism

Two machines given the same World and the same inputs must produce the same result. That requires:

  • FIFO delivery — events are processed in arrival order, not by thread scheduling.
  • Stable tie-breaks — when several things are ready, order by id.
  • No ambient time or randomness — those enter as inputs or effect results.
  • Pure functions — same inputs, same outputs.

This is also why the value graph is declared rather than tracked at run time. A declared graph has a fixed order; a tracked one depends on which reads happened first.

The pattern: execution failure is local, contract violation is fatal. A computation that cannot finish is a fact about the World; a computation that returns nonsense is a bug in the definition.

Blocked is not stale

When an upstream output is in error or unavailable, downstream consumers become blocked. They never fall back to the last good value, because that value no longer describes anything real.

If the counter's count output is in error, the gauge's display is blocked. It does not show the last number, and it does not show zero. The same rule applies at every layer: no defaults, no stale reads, no silent zero.

Effects

Some work leaves the World: an HTTP call, an AI request, a notification. Those are effects. A reducer may request one; it never performs it.

  • The request is validated and committed to an outbox with the transaction.
  • Only after the commit does the host execute it.
  • The result comes back as a new event in a later transaction.

If the transaction aborts, the effect never runs. That is the whole point: a failed transaction cannot send an email or charge a card.

Common mistakes

  1. Thinking one transaction means one input. A batch can carry many inputs; the transaction is the unit of consistency, not the unit of delivery.
  2. Expecting compute to see intermediate reducer state. Compute runs after every reducer has finished, so it sees the final state of the transaction.
  3. Treating a compute error as a transaction failure. The state transition commits; the affected output is marked error.
  4. Running an effect before commit. An aborted transaction must leave no external trace.
  5. Reading a generation that is still being published. Views consume committed generations only; a half-published frame is not a state.

Check yourself

Why do reducers run before computations?

Because computations must see the final state of the transaction. If a computation ran between two reducer deliveries, it would calculate from a state that is about to change.

A compute throws. Does the user's click get lost?

No. The state transition commits; the affected output is marked as an error. The click happened, the derived value is unavailable.

Can an effect run before commit?

Never. If it could, an aborted transaction could still have sent an email.

Why is the counter's reducer in the same event phase as the button's?

Because the button's reducer emits on_toggle during the event phase, and event emissions enqueue before the process phase. The counter's reducer handles it before any Run steps.

What does a view see while a transaction is staging?

Nothing new. It keeps showing the last committed generation. Staging is private; only the commit creates a generation.
