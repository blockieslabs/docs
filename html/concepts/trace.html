One click, row by row

A click is easy to describe and surprisingly instructive to trace. This page follows one through the document, table by table, and shows exactly what changes and what does not.

Running example

This is the dashboard reduced to three members: a button, one counter, and the gauge. The manager Run is not attached in this trace, so the process phase is empty and the focus stays on the reducer and compute path.

What the view sees

The view reads committed generations, not tables. At generation N it sees the old values; at N+1 it sees the new ones, all at once.

OutputGeneration NGeneration N+1
button.pressedfalsetrue
counter1.count01
gauge.display"0%""1%"
dashboard.count01
dashboard.display"0%""1%"

dashboard.press is an event input, so it has no generation value. It is a channel, not a cell.

Why gauge.display is not in the document

The gauge's state is {}. display is a computed output, a function of the value input and the config. If the World is reloaded, the display is recomputed from the same inputs. There is no stale string to store, and no second writer to disagree with the computation.

Two variations worth seeing

A Run claims on_press

If an attached Run claims on_press, the delivery goes to the Run's inbox instead of the button's reducer. The button's pressed stays false, because the reducer never runs. The Run handles the event in the process phase, but it cannot publish to pressed: that port is producer: compute (D-017).

This is the exclusivity rule doing its job. If the design needs pressed to update, the claim is wrong, or the Type needs a process output and the Run must publish to it. Claiming an input is taking ownership of it, not adding a listener.

The transaction aborts

If the counter reducer returns an invalid state, such as { "count": "one" }, the transaction aborts. Nothing commits: the button's pressed stays false, the counter stays 0, and the view stays at generation N. The event is not applied.

If the gauge's compute throws instead, the transaction still commits. The button and counter states are valid; the display output becomes error. The click is not lost, and the derived value is honestly unavailable. Execution failure is local; contract violation is fatal.

Check yourself

Which document rows changed?

blockies.button.state.pressed and blockies.counter1.state.count. The gauge's state is still {}, and no other table changed.

Why did the counter's reducer run in the same event phase as the button's?

The button's reducer emitted on_toggle during the event phase, and event emissions enqueue before the process phase. The counter's reducer handled it before any Run stepped.

Did the gauge's state change? Why not?

No. The gauge has no mutable state. Its display is a computed output of the value input and config, so it changes in the value phase, not in the document.

If the counter reducer returns invalid state, what does the view see?

Generation N, unchanged. The transaction aborts; nothing commits, including the button's state change.

If the gauge compute throws, what does the view see?

Generation N+1, with the button and counter states updated and display marked as error. The compute failure is local; the transaction commits.

If a Run claims on_press, does the button's reducer run?

No. The input is run-owned; the delivery goes to the Run's inbox. The reducer is not called, and the button's pressed stays unchanged.
