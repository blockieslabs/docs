Blockies / Concepts

Entities and identity

A World contains four kinds of thing. Everything else is a relationship between them, a property of them, or a value derived from them.

Running example

The dashboard contains a button, two counters, a gauge, a Composite, a manager Blockie, and an orchestrator Run. This page names what each of those is before the later pages explain how they behave.

The four kinds of thing

An entity is something that exists in its own right: it has an identity, it can be referred to, and it survives changes around it. There are exactly four, and no more.

Entity, definition, projection

Three different things get called "a thing in the World". They are not the same:

The distinction that matters: a definition is not an instance. It has an identity so it can be pinned, but it has no state and no lifecycle. A projection has neither identity nor storage; it is a function of records that do.

Identity

Every entity has an opaque identifier. "Opaque" means the system never looks inside it: it is a string, and its only job is to be stable.

Identity rules

  • Stable for the life of the entity, unique inside the World.
  • Never derived from position, display name, template path, membership, or parentage.
  • Survives movement, regrouping, and every activity the entity has ever hosted.
  • Never reused after deletion or dissolution.

A concrete test. Take counter1 and do all of this to it:

  1. Move it from (10, 10) to (200, 80).
  2. Group it into dashboard.
  3. Reparent it to a different Composite.
  4. Attach a Run, then cancel the Run.

Its ID stays counter1. Its Blueprint stays counter@1. Its state stays { count: 3 }. Only the placement, membership, and run records change. That is what "identity survives" means in practice.

A Blockie, precisely

A Blockie has four fields. That is the entire entity.

Blockie {
  id         an opaque identifier
  blueprint  a pinned Blueprint reference
  config     typed configuration
  state      typed Blockie state
}

Notice what is not there. No placement (it lives in its own table). No mode. No parent. No owner. No "is it running" flag. Each of those is either a separate record or a value computed from records that already exist.

Derived, not stored

Older drafts said a Blockie is in "drawing mode" or "computing mode". That is now derived, and the words are retired.

A Blockie is occupied if the run registry holds an activity for it that has not finished. Otherwise it is vacant. There is no field to get out of sync, because there is no field.

This is a general rule, not a special case. Occupancy, display status, availability, footprint, attention, and run counts are all functions of stored records. None is stored. The document page explains how the tables stay the only truth.

Why there is no "Computer Blockie"

An earlier design had Computer and Drawing Blockies as two primitive Blueprints. It failed for a reason worth internalising: hosting an activity is not a kind of thing, it is a relationship a thing can be in. If you make it a Blueprint, then a Blockie must switch Blueprint to start work, which breaks identity, breaks its ports, and makes "what can this Blockie become" a question with no answer.

The replacement is a rule: a Blockie's Blueprint is stable, and it may host a Run subject to the ports and claims its Blueprint declares. The Blueprints page covers those permissions.

Common mistakes

  1. Treating a Composite as a Blockie. It has no Blueprint, no state, no ports, and no appearance of its own. It is a grouping with an alias table.
  2. Treating a Run as a function call. A Run has identity, state, and a lifecycle. It can wait, be cancelled, and survive a restart. A reducer cannot.
  3. Deriving an ID from a name or position. Renaming or moving would break every reference. IDs are opaque and stable.
  4. Storing occupancy. The registry already knows. Two records of the same fact will eventually disagree.
  5. Thinking a definition is an instance. A Blueprint is a plan; a Blockie is the thing made from it. A definition has no state.

Check yourself

Is the dashboard an entity?

Yes, a Composite is one of the four entity kinds. It has identity and membership, but it is not a Blockie: no Blueprint, no state, no ports of its own.

Does counter@1 have state?

No. It is a definition: a plan. The state belongs to each Blockie that pins it. Two counters share the Blueprint and have different state.

What happens to the ID when a Blockie moves into a Composite?

Nothing. The membership edge and placement scope change; the ID, Blueprint, config, state, and ports do not.

Why is occupancy not a field on the Blockie?

Because the run registry is authoritative for it. A second field would be a second writer, and the two would eventually disagree. Derive it instead.

Is a process definition an entity?

It is one of the two definitions, and C-1 lists definitions among the four kinds. It has an identity and a digest, but no runtime state and no lifecycle. It is a pinned plan, not an inhabitant.
