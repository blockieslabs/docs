Blockies / Concepts

The document

A World is one JSON document with seven tables. It is small on purpose: everything that can be computed is absent.

Running example

The dashboard is one World. This page shows a reduced version of it as JSON: one counter, one Composite, one placement. The full example has a button, a second counter, a gauge, a manager, and two runs.

The tables

The analogy is a filing cabinet. Each drawer holds one kind of record; a drawer is not a summary of another drawer. If you want to know where something is, you open the placement drawer, not the Blockie drawer.

There is also an optional policy section holding roles and grants.

Two registries, not one

Blockies and Composites live in separate maps even though both are entities. A single map with a kind field invites code that treats them as interchangeable — which is exactly the mistake the old design made with kind: atomic | composite. The kinds meet only where a union is explicit.

Notice the division of labour. The Blockie owns identity, Blueprint, config, and state. The Composite owns membership and the alias. The placement table owns the coordinate. No table repeats another table's fact.

A Blockie is four fields

{ "id": "...", "blueprint": {...}, "config": {...}, "state": {...} }

No placement, no mode, no parent, no owner, no running flag. Every one of those is a separate table or a derivation. If a field is added later that duplicates another table, that is a bug.

Absent is not null

A Blockie with no placement is absent from placements. A dissolved Composite is absent from composites. Neither is stored as null.

This matters because absent and null mean different things throughout the protocol: a record with a null property is not the same as a record without that property, and a value that is explicitly null is not the same as a missing input.

Schema defines shape, specifications define meaning

The division

The JSON Schema answers "is this a valid record?". The specifications answer "what does this record mean, and what may happen to it?". Neither redefines the other. A field that appears in both must agree.

For example, the schema says a Run.status is one of eight strings. The process specification says which transitions are legal and who may perform them. A document can be schema-valid and still violate an invariant — which is why validation has three passes, not one.

Validation in three passes

  1. Structural — does it match the schema? Unknown fields are rejected.
  2. Cross-reference — does every reference resolve, and does every type relation hold?
  3. Invariant — one host per Run, one Composite per Blockie, acyclic containment, one producer per output, and so on.

A structural or cross-reference failure rejects the document. An invariant failure rejects too, with one exception: a dangling manager designation is repaired by clearing it, because a crashed host can leave one and refusing to open the World would be worse.

Common mistakes

  1. Putting placement on the Blockie. It is optional and lives in its own table; absence means unplaced.
  2. Adding a "running" flag. The run registry is authoritative; a flag would be a second writer.
  3. Storing a derived value. Occupancy, status, footprint, and availability are functions of records, not fields.
  4. Using null for absence. A missing record and a null value mean different things.
  5. Treating schema-valid as World-valid. Cross-reference and invariant passes exist for a reason.

Check yourself

Why is there no "is running" field on a Blockie?

The run registry already answers it. A second copy would eventually disagree with the first.

You want to add a field for "current display colour". Where does it go?

Nowhere in the document. That is renderer state. If the colour must be authored and shared, it belongs in configuration or a presentation record — not as a new top-level field.

Why is an unplaced Blockie absent rather than null?

Because null is a value and absence is not. The protocol keeps them distinct everywhere, so a missing placement must be missing, not null.

Can a document be schema-valid but still invalid?

Yes. The schema checks shape. Cross-reference and invariant passes check whether references resolve and whether the World's rules hold. All three must pass.

Where does the alias count live?

In the Composite's alias table, pointing at counter1.count. It has no state of its own; it is a public name for a port that already exists.
