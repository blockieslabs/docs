The manager's tick

A reducer finishes inside a transaction. A Run is the other half: an inbox, a process phase, and a lifecycle that can end in one atomic commit.

Running example

This is the dashboard again, now with the manager Run attached. The manager Blockie hosts orchestrator; the Run claims on_tick, reads count, and publishes status. The counter and the gauge Composite are unchanged from the previous trace.

managerBlockie is the dashboard's Brain and a direct member, which is why it can be designated as Manager. The designation and the grant are two different records: the designation is on the Composite, the grant is on the Run. The gauge Composite is a Member; its Brain and Parts are not in the grant's memberSet.

The tick

The delivery never reaches the manager's reducer. The input is claimed by the Run, so it goes to the Run's inbox; that is the exclusivity rule from the processes page.

The output is not in the document

managerBlockie.status is a producer: process value output. Its value "ok" is published in generation N+1; it is not a field in the document. If the World is reloaded, the Run resumes from its state and the output is republished when the Run next steps.

The manager's process output becomes available in the same generation as the step that published it. That is the difference between a process output and a compute output: the compute output is recomputed from values, while the process output is a published result of an activity.

The terminal commit

Now the agent cancels the Run. The cancellation is a request first, then a terminal commit.

Transaction C1 — the request

  "orchestrator": {
-   "status": "waiting",
-   "wait": { "reason": "timer", "detail": "60s" },
+   "status": "cancelling",
    "state": { "ticks": 1, "last": "ok" }
  }

The Run is still attached. The designation and the grant still exist; the process output is still available. Nothing is torn down yet.

Transaction C2 — the terminal commit

When the cancellation is acknowledged, five effects must commit together. If any one of them lands in a different generation, the World is briefly inconsistent.

  "orchestrator": {
-   "status": "cancelling",
+   "status": "cancelled",
-   "grant": { "composite": "dashboard", "memberSet": [...] }
+   // grant removed
  },
  "dashboard": {
-   "manager": { "run": "orchestrator", "epoch": 1 }

Why one generation

If the designation were cleared in a second transaction, the dashboard would briefly claim a manager that no longer exists. If the grant outlived the Run, a stale epoch could still dispatch. If the output stayed available, a consumer would read a value from a dead activity. The five effects are one fact: this manager is gone.

managerBlockie remains the dashboard's Brain and a member. Only the designation is cleared; the Blockie can host a new Run and be designated again. The gauge Composite remains a Member. The alias dashboard.status also remains, but its source is unavailable, so consumers are blocked.

If no Run is attached

The same on_tick delivery would be unclaimed. It would go to the manager's reducer, if the Blueprint has one, or be rejected. The process output status would be unavailable, because the host is vacant. A claim is what routes the event to the Run; without it, the Run never sees the event.

What did not change

  • The manager's Blockie state. It is still {}. The Run's ticks and last are Run state.
  • The counter. It still reads 1; the Run read it, it did not write it.
  • Membership and aliases. The dashboard still contains managerBlockie and gaugeWidget and still exposes status; only the designation is gone.
  • Placements. The manager did not move because its Run ended.

Check yourself

Where does on_tick go, and why not the reducer?

It goes to the Run's inbox. The input is claimed by the attached Run, and a claimed input is run-owned, not reducer-owned.

What changes in runs.orchestrator after the tick?

Status becomes waiting, a timer wait is added, state becomes { ticks: 1, last: "ok" }, and the inbox is empty. The grant and host do not change.

Does blockies.managerBlockie.state change?

No. The Run's state is separate from the host's Blockie state. The host's state is still {}.

Why does status become unavailable after termination?

Because it is a producer: process output, and its host is now vacant. A process output with no active Run is unavailable; it never falls back to the last value.

Which five effects commit together in C2?

Run terminal, host vacant, designation cleared, grant revoked, and process output unavailable. All in one generation.

If no Run were attached, what would happen to a delivery to on_tick?

It would be unclaimed, so it would go to the manager's reducer if one exists, or be rejected. The Run would never see it, and status would be unavailable.
