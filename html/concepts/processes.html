Blockies / Concepts

Processes

A Run is a long-lived activity: something that can wait, be observed, be cancelled, and survive a restart. It lives inside a Blockie, which represents it in the World.

Running example

The dashboard has a manager Blockie that hosts the orchestrator Run. The Run wakes on a timer, reads the counter, and publishes a status. The button and the counters do not need Runs; they finish inside one transaction.

Three time scales

The model has three ways to do work, and choosing the wrong one is the most common design mistake. They differ in how long they last and who owns the state.

The rule of thumb

Use a Run when the activity must outlive a transaction, wait on something uncertain, be visible as a thing in the World, or be cancellable. Otherwise use a reducer or compute.

Why a Run is not a function call

A function call is over before it returns. A Run can be between steps: waiting for a human, waiting for a timer, waiting for an external service. It needs identity so it can be addressed, state so it can resume, and a status so a person or an agent can see what it is doing.

The analogy is an employee with a task and a timesheet, not a calculator. The calculator finishes and disappears. The employee has a name, a current task, a status ("waiting for approval"), and a record of what happened. A Run is the employee; a reducer is the calculator.

A Run's own state

A Run owns its state. It never writes its host Blockie's Blockie state.

That separation is deliberate. If a Run could write the host's state, the Blockie would have two writers — its reducer and the Run — and "what is the value" would depend on which happened last. Instead, the Run publishes outward through declared ports, like everyone else.

A process definition declares three sets, and every one is validated against the host Blueprint at attach time:

Claims: who handles the event

Every event input is either reducer-owned or run-owned. Never both.

  • Claimed → the delivery goes to the Run's inbox.
  • Unclaimed → the Blockie's reducer handles it.

This is what stops double handling. Without it, an event could both update the Blockie and wake its Run, and the two could disagree. A Blockie can still have reducer behaviour on its unclaimed inputs while a Run is attached.

A concrete Run

The orchestrator is small enough to read in full. It claims one event, reads one value, publishes one value, and waits on a timer.

process orchestrator@1
  stateType: { ticks: integer, last: string }

  host:
    claims:    [ on_tick ]
    reads:     [ count ]
    publishes: [ status ]

  step(state, config, reads, inbox, grant):
    if inbox is not empty:
      state.ticks += 1
    if reads.count > 10:
      state.last = "high"
    else:
      state.last = "ok"
    publish status = state.last
    wait timer { after: 60s }

Steps

The runtime never "runs a program". It runs a bounded step and asks the definition for a result.

A step receives

  • its own state;
  • the host's configuration, read-only;
  • the resolved values of its reads ports;
  • its inbox items;
  • its dispatch grant, if it has one.

It does not receive host Blockie state, other entities, or the ambient environment.

A step returns

Result containsMeaningExample
outcometerminal: succeeded, failed, or cancelled"the report is finished"
waitthe Run is waiting, with a reason"waiting for a human approval"
neithercontinue — step me again in a later transaction"not finished, not waiting"

That third case is how loops are expressed. There is no continue flag; a loop is just a Run that keeps saying "not finished, not waiting".

Two rules make this predictable:

  • One step per Run per transaction. A Run cannot loop inside a commit (P-24).
  • Runs never observe a value change in the transaction that produced it. Values stabilise after the process phase, so a Run always reads one coherent generation (P-34).

That second rule is glitch-freedom by construction, not a limitation to work around.

The lifecycle

Waiting and suspended are different. Waiting means the Run has an unsatisfied condition and will continue. Suspended means something is deliberately holding it back.

The reason is not decoration: it is the difference between "nobody needs to do anything" and "this is blocked on a human". That distinction is what a status badge shows.

Dispatch

A Run holding the composite.dispatch grant may send an addressed event to a member. The destination must be in its declared member set, so the possible routes are known in advance even though the choice is made at run time.

The new event gets a new id and records causation pointing at the event that triggered it. That chain is how you reconstruct "why did this happen" later.

In the dashboard, the orchestrator can dispatch increment to counter 2 when the count is low. It cannot add a member, move a member, read a member's Blockie state, or cancel a member's Run; its grant is exactly one verb, scoped to the Composite (S-14).

Failures

What happenedResult
The step throws, traps, or runs out of budgetthe Run fails; the transaction still commits
The step returns an invalid value or an undeclared targetthe whole transaction aborts
The inbox delivery itself is invalidthe transaction aborts

Executing badly is a legitimate outcome. Lying about your contract is a bug. The split matters: a failed Run is a fact about the World and can be retried; a contract violation means the definition is wrong and must not commit.

Cancellation

Cancellation is a request, not a kill. The Run moves to cancelling, the step acknowledges, and only after a grace period is it forced. When a Run ends, its descendants are asked to cancel too — each one goes through the same path, so the history stays honest.

If the host Blockie is deleted, the Run must be terminated first, in the same transaction (P-42). A Run never outlives its host.

Check yourself

A button needs to respond to clicks. Does it need a Run?

Not necessarily. A reducer can toggle state and emit an event on click. A Run is only needed if the response must outlive the transaction, wait, or be visible and cancellable.

Why can't a Run read the host's Blockie state?

Because that state changes under the reducer. A reader with no dependency edge would see values that do not belong to one coherent generation. The Run gets declared input values instead, which stabilise before it steps.

A step returns neither an outcome nor a wait. What happens?

The Run goes back to queued and is stepped again in a later transaction. That is how a loop is expressed, bounded by one step per transaction.

What happens to a claimed event input?

The delivery goes to the Run's inbox, not the Blockie's reducer. The two are exclusive; an input is reducer-owned or run-owned, never both.

Can a manager Run remove a member from its Composite?

No. Its grant is composite.dispatch only. Membership changes need a document transaction under a mutate grant held by an actor, not by the Run.
