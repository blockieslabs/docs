Blockies / Concepts

The running example

One small World, used by every concept page. It has a button, two counters, a gauge, a Composite that groups them, a Run that manages the group, and two views with different permissions.

Concepts are easier to hold when they all point at the same thing. This page is that thing. Every other concept page refers back to it: "the button", "the dashboard", "the manager run". Nothing here is special; it is an ordinary World, small enough to fit on one screen.

The two Blueprints that carry most of the lesson

A Blueprint is the plan for a Blockie. The button and the counter are small enough to read in full, and they show the difference between config, Blockie state, compute, and reduce.

button@1

blueprint button@1
  appearance: rounded-rect-2d + renderer/button

  state:  { pressed: boolean }   initial { pressed: false }
  config: { label: string }      defaults { label: "Press" }

  ports:
    on_press   event in
    on_toggle  event out
    pressed    value out boolean, producer: compute

  reduce(state, config, event):
    on on_press:
      next.pressed = not state.pressed
      emit on_toggle

  compute(state, config):
    pressed = state.pressed

counter@1

blueprint counter@1
  appearance: rounded-rect-2d + renderer/counter

  state:  { count: integer }    initial { count: 0 }
  config: { step: integer }     defaults { step: 1 }

  ports:
    increment  event in
    count      value out integer, producer: compute

  reduce(state, config, event):
    on increment:
      next.count = state.count + config.step

  compute(state, config):
    count = state.count

Two Blockies can share a Blueprint and differ only in config. Counter 1 and counter 2 are both counter@1; one might have step: 1 and the other step: 10. That is the point of config: it parameterises the instance without forking the Blueprint.

The flow, end to end

A presenter presses the button. One transaction carries the event through the reducer, the counter, the gauge, and the commit. This is the sequence every concept page will refer to.

Three different time scales appear in that diagram, and keeping them apart is most of the model:

The Composite

The dashboard is a grouping, not a Blockie. It owns membership edges, aliases, a fold, and a manager designation. It has no ports of its own: the aliases are its interface.

dashboard

composite dashboard
  origin: grouping

  members:
    button
    counter 1
    counter 2
    gauge

  aliases:
    press    -> button.on_press
    total    -> fold(sum, [counter 1.count, counter 2.count])
    display  -> gauge.display

  manager: manager Blockie
  presentation: { label: "Sales dashboard", body: gauge }

Two connections make the flow work. They are separate from membership: being in the same Composite does not connect anything.

connection button.on_toggle -> counter 1.increment
connection button.on_toggle -> counter 2.increment
connection counter 1.count  -> gauge.value

The Run

The manager Blockie hosts a Run. The Run has its own state, claims one event input, reads one value, and publishes one process output. It never writes the manager's Blockie state.

orchestrator@1

process orchestrator@1
  stateType: { ticks: integer, last: string }

  host:
    claims:    [ on_tick ]
    reads:     [ count ]
    publishes: [ status ]

  step(state, config, reads, inbox, grant):
    if inbox is not empty:
      state.ticks += 1
    if reads.count > 10:
      state.last = "high"
    else:
      state.last = "ok"
    publish status = state.last
    wait timer { after: 60s }

The Run is what makes the manager an activity rather than a value. It can wait, be cancelled, be observed, and survive a restart. The counter does not need any of that: it is a reducer plus a compute, and it finishes inside one transaction.

Two views, one World

The presenter and the audience see the same Blockies. They differ in viewport, renderer, and grant set. The audience view is not a copy of the World, and the renderer is not the thing that hides the button.

What to notice

  • The button and the counter share a shape. Both are Blockies with a Blueprint, config, state, and ports. The difference is their Blueprint, not their kind.
  • The gauge has no mutable state. Its output is a pure function of its input and config. A Type does not need state to be useful.
  • The dashboard has no ports. Its interface is the alias table. A Composite is not a Blockie with extra steps.
  • The manager Run is not the manager Blockie. The Blockie is the in-world body; the Run is the activity. The Run owns its state; the Blockie owns its own.
  • Membership, placement, connection, and authority are four different facts. The counter is a member of the dashboard, placed at a coordinate, connected to the button, and readable by the audience. None of those implies the others.

Check yourself

Why can counter 1 and counter 2 share a Blueprint but behave differently?

Because the Blueprint declares the shape and the logic, and config supplies the per-instance parameters. If one has step: 1 and the other step: 10, the same reducer produces different counts. If the behaviour itself differed, they would need different Blueprints.

Why is the dashboard not a Blockie?

Because it has no Blueprint, no state, no ports, and no appearance of its own. It is a grouping: membership edges, an alias table, a fold, a manager designation, and optional presentation. Making it a Blockie would give it a second identity and a second way to be controlled.

Why does the gauge not need a reducer?

It has no event input and no mutable state. Its output is computed from its input value and config. A reducer is only needed when an event must change owned state.

Who may press the button: the presenter, the audience, or the manager Run?

The presenter, through a deliver grant on the press alias. The audience is read-only in this example. The manager Run holds composite.dispatch, so it can send an addressed event to a member, but that is a different path from an external deliver; in this example it dispatches increments, not presses.
