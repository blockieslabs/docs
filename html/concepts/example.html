Blockies / Concepts

The running example

One small World, used by every concept page. It has a button, two counters, a gauge made of three cells, a dashboard that contains them, a manager Run, and two views.

Concepts are easier to hold when they all point at the same thing. This page is that thing. Every other concept page refers back to it: "the button", "the gauge", "the dashboard", "the manager". Nothing here is special; it is an ordinary World, small enough to fit on one screen.

The two Composites are the point. The gauge is a multi-cell widget: its brain owns the behavior, its parts render the segments. The dashboard is a larger Composite: its brain is the manager, and its members are independent widgets, one of which is the gauge Composite.

The gauge: one brain, two parts

The gauge is three cells. The brain is a Blockie; the two segments are Blockies. The brain listens to count, computes a normalized level, and publishes it to both parts. Each part computes its own fill from level and its index config.

gauge@1 — the brain

blueprint gauge@1
  appearance: gauge-frame-2d + renderer/gauge

  state:  {}                          // compute-only
  config: { min: 0, max: 100, unit: "%", segments: 2 }

  ports:
    count    value in  number
    level    value out number, producer: compute
    display  value out string, producer: compute

  compute(state, config, count):
    level   = clamp((count - config.min) / (config.max - config.min), 0, 1)
    display = format(count, config.unit)

gauge-segment@1 — a part

blueprint gauge-segment@1
  appearance: gauge-segment-2d + renderer/segment

  state:  {}                          // compute-only
  config: { index: integer, segments: integer }

  ports:
    level  value in  number
    fill   value out number, producer: compute

  compute(state, config, level):
    fill = clamp(level * config.segments - config.index, 0, 1)

gaugeWidget — the Composite

composite gaugeWidget
  brain: gaugeBrain
  parts:
    gaugeSegment0
    gaugeSegment1

  aliases:
    count    -> gaugeBrain.count
    display  -> gaugeBrain.display

  connections:
    gaugeBrain.level -> gaugeSegment0.level
    gaugeBrain.level -> gaugeSegment1.level

The Parts' index configs live on the Blockies, not on the Composite: gaugeSegment0 has config.index = 0, and gaugeSegment1 has config.index = 1. The Composite only holds the role edges.

The gauge has no Run. Its brain is a compute-only Blockie: it reads a value, computes values, and finishes inside the transaction. A Run would be needed only if the gauge had to wait, call outside, or be cancelled.

The dashboard: one brain, four members

The dashboard is a Composite of independent widgets. Its brain is the manager Blockie; its members are the button, both counters, and the gauge Composite. The gauge is a member, not a part, because it has its own brain and its own behavior.

dashboard — the Composite

composite dashboard
  brain: managerBlockie
  members:
    button       { role: member }
    counter1     { role: member }
    counter2     { role: member }
    gaugeWidget  { role: member }

  aliases:
    press    -> button.on_press
    count    -> counter1.count
    display  -> gaugeWidget.display
    status   -> managerBlockie.status

  fold total = sum(counter1.count, counter2.count)
  manager: orchestrator, hosted by managerBlockie
  presentation: { label: "Sales dashboard", body: gaugeWidget }

The manager Run claims on_tick, reads counter1.count, and publishes status. It can dispatch to Members; it cannot dispatch to the gauge's parts, because parts are not in its memberSet.

orchestrator@1 — the manager Run

process orchestrator@1
  stateType: { ticks: integer, last: string }

  host:
    claims:    [ on_tick ]
    reads:     [ count ]
    publishes: [ status ]

  step(state, config, reads, inbox, grant):
    if inbox is not empty:
      state.ticks += 1
    state.last = reads.count > 10 ? "high" : "ok"
    publish status = state.last
    wait timer { after: 60s }

The button and the counters

These are single-cell Blockies. The button has a reducer and a compute; the counter has a reducer and a compute. Neither needs a Run.

button@1

blueprint button@1
  appearance: rounded-rect-2d + renderer/button
  state:  { pressed: boolean }   initial { pressed: false }
  config: { label: string }      defaults { label: "Press" }

  ports:
    on_press   event in
    on_toggle  event out
    pressed    value out boolean, producer: compute

  reduce(state, config, event):
    on on_press:
      next.pressed = not state.pressed
      emit on_toggle

  compute(state, config):
    pressed = state.pressed

counter@1

blueprint counter@1
  appearance: rounded-rect-2d + renderer/counter
  state:  { count: integer }    initial { count: 0 }
  config: { step: integer }     defaults { step: 1 }

  ports:
    increment  event in
    count      value out integer, producer: compute

  reduce(state, config, event):
    on increment:
      next.count = state.count + config.step

  compute(state, config):
    count = state.count

The flow, end to end

A presenter presses the button. The counter increments, the gauge brain recomputes, and the gauge segments recompute. The document changes only the button and counter rows; the gauge is compute-only.

The two views

The presenter and the audience see the same World. They differ in viewport, renderer, and grant set. The audience view is not a copy, and the renderer is not the thing that hides the button.

What to notice

  • The gauge is a Composite, not a Blockie. It is three cells: one brain and two parts. A single Blockie cannot grow to three cells.
  • The dashboard is also a Composite. Its members are independent widgets; one of them is the gauge Composite. The tree is recursive.
  • Brain and Manager are different roles. gaugeBrain is a compute-only brain. managerBlockie is the dashboard's brain and hosts the manager Run.
  • Parts and Members are different roles. The gauge segments are parts: visual, vacant, driven by the brain. The button, counters, and gauge are members: independent, with their own behavior.
  • Identities and Blueprints are different. gaugeBrain is a Blockie identity; gauge@1 is the Blueprint it pins.
  • The gauge can grow. Add another gauge-segment@1 with the next index; the brain's segments config and level fan-out handle it. The dashboard does not change.

Check yourself

How many cells does the gauge have?

Three: one brain (gaugeBrain) and two parts (gaugeSegment0, gaugeSegment1).

Is the gauge a Blockie?

No. It is a Composite. The brain and each part are Blockies; the gauge is the assembly.

Which is the dashboard's brain, and which is its manager?

managerBlockie is the brain. The orchestrator Run it hosts is the manager. The brain is a Blockie role; the manager is a Run role.

Does the gauge have a Run?

No. Its brain is compute-only. A Run is only needed when the activity must wait, call outside, be observed, or be cancelled.

Can the dashboard's manager dispatch to a gauge segment?

No. The segments are Parts, not Members. They are not in the manager's memberSet; the gauge's brain drives them internally.

What is gauge@1?

A Blueprint reference: the id gauge, version 1. It is not an identity. gaugeBrain is the Blockie that pins it.
