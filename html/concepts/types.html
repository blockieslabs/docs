Blockies / Concepts

Blueprints, state and ports

A Blueprint is the plan a Blockie is made from. It decides what the Blockie looks like, what data it owns, and what it can talk to. The hard part is keeping the Blueprint, the value types inside it, and the appearance apart.

Running example

The dashboard has a button, two counters, and a gauge. This page uses the button, the counter, and the gauge, because they are small enough to read in full.

Three words that look alike

"Type" used to mean two different things, so the vocabulary now separates them. When you read the rest of the guide, hold these three apart:

WordWhat it isExample
BlueprintThe immutable, digest-pinned plan for a Blockiecounter@1

A value type is not a Blueprint. { count: integer } describes the shape of the counter's state; it does not say what the counter looks like, what it can do, or how it behaves. A Blueprint contains value types. The schema calls a value type BtsType, from the Blockies Value Type System (BTS).

Blueprint vs Blockie

A Blueprint is a recipe; a Blockie is a cake. The recipe is immutable and shared. Each cake has its own config and its own state, and changing one cake does not change the recipe or the other cakes.

Counter 1 and counter 2 are both counter@1. They differ only in config:

In the document, an instance is just a pinned Blueprint plus two values:

{
  "id": "counter1",
  "blueprint": { "id": "counter", "version": "1.0.0", "digest": "sha256:..." },
  "config": { "step": 1 },
  "state":  { "count": 0 }
}

If the behaviour itself differed, not just the parameter, they would need different Blueprints. Config is for the same plan with different settings; a different plan is a different Blueprint.

The test

If it changes because of an event, it is state. If it changes because someone configured the instance, it is config. Putting step in state would force every counter to spend a reducer transition to change a setting; putting count in config would make the counter unable to count.

Why does the distinction matter beyond tidiness? Because a config change and a state change have different consequences. A config change takes effect at the next step and does not wake a waiting Run (P-21, D-040). A state change can propagate through compute to a value output, and that output can satisfy a Run's dependency wait (P-33). Same storage, different behaviour.

Value vs event

A value is the latest information, like a variable. An event is a discrete occurrence, like a message. The difference is not stylistic: a button press cannot be a boolean that stays true, because the second press would be invisible.

The correction most people need

compute does not change Blockie state. It is pure: it reads state, config, and input values, and returns output values. The reducer changes state. A process changes Run state, and publishes to the host's process outputs; it never writes the host's Blockie state (C-45).

Why not use a process for every value? Because a Run has identity, lifecycle, persistence, scheduling, and a step budget. For a formatting function, that is enormous overhead, and it makes the output unavailable whenever no Run is attached. A compute output is available as long as its inputs are. D-011's "no performance tier of process" means exactly this: compute is the synchronous dataflow path, not a fast process.

The three functions

A Blueprint may declare two functions; a Process definition declares a third. They run at different times and have different authority.

The ordering is not arbitrary. Reducers run first, so compute sees the final state of the transaction. Steps run before compute, so a step's published value is visible in the same generation. A compute never runs between two reducer deliveries, because it would calculate from a state that is about to change.

What a reducer looks like

A reducer handles one event and returns the complete next state. It may also emit events, request effects, or dispatch to a member, but it cannot wait and it cannot call outside.

reduce(state, config, event):
  on increment:
    next.count = state.count + (event.by ?? config.step)
  on reset:
    next.count = 0

Two properties matter. It is pure: the same state, config, and event always produce the same next state. And it is exclusive: if the event input is claimed by an attached Run, the reducer never sees the event at all. The delivery goes to the Run's inbox instead (P-15, P-16).

Five mistakes this page is trying to prevent

  1. Using "Type" for both things. Say Blueprint for the plan, value type for the shape. If a sentence works with both, it is ambiguous.
  2. Putting a setting in state. If it changes because someone configured the instance, it is config. If it changes because of an event, it is state.
  3. Expecting compute to change state. Compute is pure. The reducer owns state; compute publishes values derived from it.
  4. Using a process for a cheap derived value. A process makes the value unavailable when no Run is attached, and pays identity and scheduling for a formatting function.
  5. Treating a process port as having a default. A process port with no attached Run is unavailable. Consumers are blocked; they never see a default or a stale value (C-32).

The rules, in one place

  • C-33. A Blueprint declares an appearance, state and config schemas with initial values, ports, and optional compute and reduce logic.
  • C-34. Every port declares direction, kind, and a value type. A value output may declare producer: compute | process. An event input may declare claimable: true.
  • C-35. A Blockie has at most one effective producer per value output, and never exposes a port its Blueprint does not declare.
  • C-36. A Blueprint is immutable once published; changing it means a new version.
  • C-45. A Run never writes the World document and never writes its host's Blockie state.
  • P-5. Run state is owned by the Run, never by the host's reducer or compute.
  • D-017. A value output is produced by compute or by a process, never both.

Check yourself

Is { count: integer } a Blueprint?

No. It is a value type: the shape of a value. A Blueprint is the whole plan, and it contains this value type as its state schema.

A counter's step is 10. Is that config or state?

Config. It parameterises the instance and is set by a document transaction. The current count is state, because the reducer changes it when an event arrives.

Can compute change state.count?

No. Compute is pure; it reads state and returns output values. The reducer changes state.count in the event phase.

A process port has no attached Run. What does a consumer read?

Nothing. The port is unavailable, and the consumer is blocked. It never falls back to a default or the last value (C-32).

Why can't a button press be a boolean value input?

Because a boolean describes what is true now, not what happened. The second press would leave the value unchanged and be invisible. A press is an event; pressed is the value that results from it.
