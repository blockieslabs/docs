Performance

Most of the performance of this system is decided by the architecture, not by tuning at the end. This section maps where the cost goes, layer by layer, and what removes it.

The uncomfortable truth

A naive implementation of this design is not slightly slow. It is slow in a way that gets worse as the World grows, because several of the architecture's best properties are also expensive if you take them literally.

Take one example. The specification says occupancy and status are derived, never stored (C-14). Read that as "compute it when asked" and every status query scans the run table. A frame that asks for the status of every Blockie is then O(N × R): at ten thousand Blockies and a thousand runs, ten million comparisons per frame, before anything is drawn.

The fix is not to store the value. It is to notice that derived does not mean uncached. A transient index that is rebuilt at load, updated in the same transaction, never serialised and never authoritative is not a stored derived value. It is a cache with a proof obligation.

The distinction this section keeps returning to

A stored derived value is a second source of truth. A cached derived value is a function of the first truth, with a generation stamp. The first is forbidden. The second is how the engine reaches its performance budget.

There are 120 findings in the reference document. Each one is tagged by layer, scope, the scale at which it starts to hurt, and whether the cost is forced by a requirement or is just a representation choice. That tagging is what makes the list usable: it tells you which costs you can design away and which ones you have to amortise.

How to read a finding

Every finding has the same shape, so you can decide in a few seconds whether it applies to you.

PF-028 · Fixpoint stabilisation

Layer: A1 Core. Scope: per transaction. Trigger: T1, visible at a thousand entities. Class: architectural: the value phase is required, but the way it is evaluated is not.

What happens: the stabiliser loops over every node until nothing changes. On a chain of length G, that is O(G²) visits.

Fix: precompute a topological order once per graph revision, then walk it once with a dirty-closure worklist. Most transactions touch a handful of nodes.

The rule that keeps this honest

A fix may not change an observable trace, and it may not move authority. Caching, batching, indexing and parallelism may change when work happens, never who may do it. If a technique changes the result of a transaction, it is a semantic amendment and belongs in the decision log.

What the architecture already gets right

This is not a rescue plan. Several decisions are performance-positive and should not be traded away for a benchmark.

Free wins already in the design
  • Declared graph, not runtime tracking. No per-read bookkeeping, no proxy objects, no dependency discovery at run time (D-011).
  • Views are filters, not copies. One World, many cameras, so memory does not multiply by the number of screens (D-007).
  • Geometry is inert. A spatial index can be approximate, rebuilt or GPU-resident without touching a trace (C-23).
  • Definitions are immutable and digest-pinned. Compiled modules, validators and renderers are cacheable forever (C-36).
  • Steps are bounded and never span a commit. Latency has a ceiling and cancellation has a clean point (P-23).
  • Absence is not null. Sparse tables stay sparse; there is no sentinel value to scan past (C-13).

Check yourself

Why is a cached derived value not a violation of C-14?

C-14 forbids storing derived values in the document, because a stored value gets a second writer and eventually disagrees with its source. A transient cache is rebuilt from the source, updated in the same transaction, never serialised and never authoritative. It is a function of the truth, not a copy of it.

Why does one transaction per input hurt even when each input is tiny?

Because the fixed cost of a transaction, especially fsync and publish, is paid per transaction, not per byte. A keystroke that changes one value still pays a database commit. Batching amortises the fixed cost without changing what a transaction means.

What is the difference between an architectural finding and an implementation finding?

An architectural finding is a cost forced by a requirement: you cannot remove it without changing semantics, so you amortise it. An implementation finding is a representation choice: the requirement is satisfied either way, and one way is simply faster.
