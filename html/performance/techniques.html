Techniques and tradeoffs

A reverse lookup: given a technique, what does it fix? And which "fixes" would break the architecture?

How to use this page

Start from a symptom, not from a technique. "Status queries are slow" points at indexing. "The frame is over budget" points at draw calls and text. "Commits take ten milliseconds" points at fsync and serialisation. The tables below go the other way: each technique lists the findings it addresses, so you can check whether a change is aimed at the right cost.

Two rules that outrank every technique

A fix may not change an observable trace, and it may not move authority. Caching, batching, indexing and parallelism may change when work happens, never who may do it. If a technique changes the result of a transaction, it is a semantic amendment and belongs in the decision log.

Open decisions

These need a decision record, not an implementation choice. Each one changes what "fast" means, so an engine should not guess.

  1. Derived caches are not stored state. Clarify C-14: a transient, rebuilt, non-authoritative index is permitted. Without this, implementers choose between a violation and a scan.
  2. Canonical encoding. Key order, number form, decimal form, and whether the digest is over entities or chunks. Needed for reproducible definitions, Merkle sync and reproducible builds.
  3. Fold reduction order. sum over floats is order-sensitive. Decide member-ID order, a fixed tree, or exact arithmetic. This is a semantic decision, not an optimisation.
  4. Steps per transaction. P-24 says one. Decide whether a bounded K is allowed, and whether a turn is the supported latency mechanism.
  5. Run archiving. Decide whether terminal runs move to a cold partition in the document, and how acknowledgement and C-9 survive the move.
  6. Parallelism policy. Decide whether A1 may evaluate topological levels in parallel, and what the deterministic merge rule is. Data parallelism inside a node is uncontroversial; task parallelism is not.
  7. View interest model. Decide whether interest is viewport-derived, grant-derived, or declared. This determines whether PF-079 is a cache or a protocol feature.

Check yourself

You have a slow status query. Do you reach for SIMD or for an index?

An index. SIMD makes a scan faster by a constant factor; an index removes the scan. Reach for SIMD when the algorithm is already right and the loop is the bottleneck.

You want to parallelise the value phase. What must you decide first?

The merge rule and the reduction order. If two orders produce different values, the digest diverges. Data parallelism inside a node is safe; task parallelism across nodes needs a deterministic merge.

Why is "cache the status in the document" not the same as "cache the status in memory"?

The document survives restarts and can be edited by another writer, so the cache becomes a second source of truth. In-memory state is rebuilt from the tables and can be discarded at any time, so it remains a function of the truth.

What is the first metric to instrument?

Transaction time split by phase. It tells you whether you are paying for commit, stabilisation, or the sandbox, which determines which page of this section applies.
