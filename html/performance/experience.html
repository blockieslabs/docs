Drawing and observing

The last mile: what the renderer draws, what the client receives, and what the agent reads. This is where a correct engine still feels slow.

Draw calls are the budget

A frame has about 16.6 ms at 60 Hz. A draw call costs 1–10 µs of CPU before the GPU sees anything. Ten thousand entities drawn one at a time is 10–100 ms of CPU, so the frame is already gone before the first pixel is shaded.

Instance by archetype. One instanced draw per Type, renderer and material. Instance data is a SoA buffer: position, scale, colour, texture index. A Type with ten thousand instances is one call. A texture atlas removes the bind changes between instances.

CostPer entityAt 10k
Draw call or state change1–10 µs10–100 ms
Transform update50–200 ns0.5–2 ms
Text shaping and layout10–100 µs100–1000 ms

Text is the worst of the three. A dashboard of ten thousand labels cannot shape text per label per frame. Cache the layout keyed by string, style, size and device pixel ratio; use a glyph atlas and SDF fonts so a scale change does not re-shape.

Transforms should be retained, not recomputed. A placement change marks a subtree dirty and the transform pass walks parents before children. The renderer reads a flat world-space array. The same dirty propagation gives footprints and LOD counts for free.

Only draw what can be seen

A viewport is a query, not a loop. Build a quadtree or BVH per generation, share it across views, and let each view keep a visible bitset. Frustum culling removes what is offscreen; occlusion culling removes what is behind something; LOD reduces what is far away. At the large end, put the culling on the GPU with a compute shader and an indirect draw, so the CPU never touches per-entity data.

Hit testing uses the same index. Only Blockies are hit-tested (S-40), so Composite chrome never enters the candidate set. Broadphase by AABB, narrowphase by the Type's archetype. A pointer move should not scan ten thousand entities.

On-demand frames

If nothing changed and no animation is running, do not draw. A committed generation is the only thing that can start a frame, unless an animation is in flight. Busy-polling at 60 Hz while the World is idle is pure waste, and on a laptop it is a battery complaint.

Clients are thin, but not free

A client consumes committed generations and sends authorised commands. It should not re-implement protocol semantics. But "thin" does not mean "no state": the client still has to apply patches, keep an index, and show feedback before the round trip finishes.

  • Apply patches by handle. A client-side index mirroring the host's makes a patch an array write, not a scan.
  • Cold load from a binary snapshot. Parsing a large JSON document at startup is a visible delay; a binary format with lazy sections starts drawing sooner.
  • Predict input locally. Show the pressed state immediately, then reconcile when the commit arrives. The prediction is presentation only; it never changes a value.
  • Share decoded assets. Decode once per process, keyed by content digest, not once per view.

Agents read projections, not Worlds

An agent is an operator: it issues authorised commands and events. It is also the most expensive reader in the system, because everything it reads goes into a context window.

Serialising the whole World on every turn is the agent equivalent of drawing every entity at 60 Hz. It is also mostly irrelevant: the agent usually needs a scope, a few fields, and what changed since last time.

Three rules make agent operation cheap:

  • Query with a scope. A viewport, a Composite, a run tree, a named set. The same interest index that serves views serves agents.
  • Project fields. Status and a label are enough for most decisions; the state blob is not.
  • Send diffs. "Since your last turn: these twelve entities changed" is smaller and more useful than the current state of everything.

Commands get the same treatment. An agent that issues one command per intent pays one transaction per intent. A batch or patch API, with idempotency keys, turns a plan into one round trip. And an LLM call is not a computation: model it as an effect plus an external_service wait, so the run suspends instead of blocking a loop iteration.

Check yourself

Why does instancing help even when the GPU is fast?

Because the cost is on the CPU before the GPU sees anything: validating state, binding resources, submitting work. Ten thousand submissions is milliseconds of CPU per frame, regardless of how fast the shading is.

Why is text the worst per-entity cost?

Shaping and layout are tens to hundreds of microseconds per label, against nanoseconds for a transform. Ten thousand labels cannot be laid out per frame; they have to be cached by content and style.

What should an agent read instead of the World?

A scoped projection: the entities in its viewport or Composite, a few fields, and the diff since its last turn. The same interest index that serves views can serve the agent.

Why is an LLM call an effect rather than a computation?

Because it is slow, external and uncertain. Modelling it as an effect plus an external_service wait lets the run suspend without blocking the loop, and lets the result arrive as an event in a later transaction.
