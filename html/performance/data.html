Data and indexes

The document is a wire format. The runtime is a data structure. Confusing the two is the most common way to make this architecture slow.

The document is not the data structure

The schema describes a World as JSON: Record<Id, Blockie>, Record<Id, Run>, and so on. That shape is chosen for validation, diffing and human reading. It is a good file format and a poor runtime layout.

Using it directly means every lookup hashes a string, every entity is a small hash table with boxed values, and iterating one field pulls the whole record into cache. The cost is not theoretical: a JSON-shaped entity can be five to twenty times larger than a packed one, and a scan that should touch one cache line per sixteen entities touches one per entity.

The fix is not to change the schema. Parse once at load into a runtime layout, and project back at save. The document stays the same; the engine gets a shape it can iterate.

The boundary rule

JSON lives at the edge: load, save, network, conformance vectors. Inside the engine, entities are handles, fields are columns, and edges are contiguous arrays. Nothing in the specifications requires the in-memory form to match the wire form.

Derived values are not stored, but they can be cached

C-14 says occupancy, footprint, display status, availability and run counts must not be stored. The reason is sound: a stored derived value gets a second writer, and the two writers eventually disagree.

But there is a difference between storing a derived value and materialising it. A cache that is rebuilt at load, updated in the same transaction as its inputs, never serialised, and never authoritative is not a second source of truth. It is a function of the first truth with a generation stamp.

Without that distinction an implementer has two bad choices: violate C-14, or scan on every query. The second is the one that quietly kills the frame budget.

A status query implemented as "scan the run table for a non-terminal run whose host is this Blockie" is O(R) per call. A frame that asks for the status of every Blockie is O(N × R). At ten thousand Blockies and a thousand runs, that is ten million comparisons per frame, and the same shape repeats for every derived projection.

These are secondary indexes in the database sense. Build them once at load, update them inside the transaction that changes the source, roll them back with the undo journal, and never serialise them. Each entry carries the generation that produced it, so a stale entry is detectable rather than silently wrong.

The proof obligation

For every committed generation, index(x) = derive(tables, x). If an index disagrees with the registry, the index is wrong and must be rebuilt. A debug build should assert this on every commit. The cache is allowed to be fast; it is not allowed to be a second opinion.

Layout decides the constant factor

Two entities with the same fields can cost very different amounts to iterate. The difference is whether the fields you read are next to each other in memory.

A frame that reads status for ten thousand entities touches ten thousand records in AoS and one sixteenth of that in SoA. The difference is a cache miss per entity: roughly 100 ns × 10k = 1 ms, per pass, per view. That is a sixth of a 60 Hz frame budget spent on reading one field.

Handles, not pointers

Give every entity a dense integer index plus a generation counter. The index makes arrays possible; the generation makes deletion detectable without reusing an identity (C-10). Keep one canonical string table for the document and for traces. Internal code never hashes a string.

A handle is not an ID. It must never leak into the document, a digest, or a trace that is compared across hosts. It is a cache address, not an identity.

Edges as contiguous arrays

Membership, connections and aliases are adjacency lists. Store them in compressed sparse row form: one offsets array and one targets array. Iterating a Composite's members becomes a contiguous scan instead of a chain of hash lookups. This is also what makes a fold over ten thousand members vectorisable.

Archetypes for Type dispatch

Group entities by Type so a renderer or a compute kernel sees one contiguous block per Type. This removes a branch or virtual call per entity and makes the kernel's input layout predictable. It is the same idea as an entity-component-system archetype, without changing the ontology: the Type is already the grouping key.

Identity is an index, not a string

IDs are opaque, stable, unique and never reused (C-7–C-10). They are not required to be random. A1 also has no ambient time or randomness, so random UUIDs were never legal: replay would diverge.

A per-World monotonic counter gives deterministic, sortable IDs. Encode (world epoch, counter) in a fixed-width big-endian value, so bytewise order equals creation order. Deleted IDs are never reused because the counter only moves forward. The counter is part of the document, or derived as the maximum existing value plus one at load.

Then intern: map every ID to its rank in creation order. P-29's "ascending Run ID, bytewise" becomes an integer compare. Keep the string form for the document and for traces.

Sort per arrival, not globally

P-29 orders runs that become ready at the same point. A global priority queue keyed by string ID re-sorts everything and compares strings at every level. A FIFO of buckets, each sorted by integer rank, satisfies the same rule in O(k log k) per bucket.

Port names repeat everywhere: every Blockie of a Type has the same ports. A global symbol table with integer symbols turns port lookup into an array index, and makes subset checks (P-3's claims ⊆ claimable) a few bitwise operations.

Geometry is a tree with a cache

Placement is hierarchical and local (C-17). Resolving a world transform is a walk to the root: O(D) matrix compositions. Doing that per entity per frame is O(N × D). At ten thousand entities and depth ten, that is a hundred thousand matrix multiplies per frame, plus a pointer chase for each parent.

Cache each world transform. A change marks the entity and its descendants dirty, and the recompute walks parents before children. Unchanged subtrees cost nothing. The renderer then reads flat world-space arrays: x, y, scale, layer.

Footprints use the same trick. A placement change updates the entity's local AABB and propagates the union to ancestors until the value stops changing. A footprint query is then O(1).

Why the spatial index is free

C-23 says randomising every coordinate must leave every execution trace unchanged. That makes the spatial index a pure presentation cache: it can be approximate, rebuilt per frame, LOD-specific, or GPU-resident, with no semantic risk. Most engines cannot say that.

Validation should scale with the change

Validation is three passes: structural, cross-reference, invariant (C-48). Running all three over the whole document on every commit is O(W) per transaction, which is O(T × W) per session.

Run the full pass at load and on demand. At commit, validate the write set: the touched entities, the invariants that involve them, and the cross-references that point at them. A debug build can run both and compare.

Three quadratic traps need specific fixes:

  • Acyclicity per add_member. A fresh DFS is O(V+E). Adding N members one at a time is O(N²). Maintain a dynamic topological order; a cycle exists iff the target already precedes the source, which is O(1) amortised.
  • Template instantiation. The template was validated when it was published. Instantiation needs to check the new edges, not re-prove the template. Allocate an ID block, build the edges, run one cycle check over the new subgraph.
  • State validation after every step. A generic JSON Schema validator runs at 1–10 MB/s. Compile each state type to a predicate or bytecode once per digest (P-6).

Check yourself

Why can a cache be correct when a stored value would not be?

Because the cache has no independent authority. It is rebuilt from the tables, updated in the same transaction, and can be discarded at any time. A stored value survives a restart and can be edited by a second writer, which is what creates disagreement.

What does a handle give you that a string ID does not?

An array index. It makes columns and contiguous edge lists possible, so iteration is a scan instead of a hash lookup. It is not an identity: the canonical string remains the ID, and the generation counter prevents a deleted handle from being mistaken for a new entity.

Why is the spatial index allowed to be approximate?

Because geometry is semantically inert (C-23). Randomising every coordinate must leave every execution trace unchanged, so a spatial index can only affect what is drawn or clicked, never what a transaction does.

Why does adding members one at a time become quadratic?

Each add runs a cycle check over the whole containment graph. N adds of O(N) each is O(N²). A maintained topological order makes each check constant amortised, and a bulk operation can prove acyclicity once.
