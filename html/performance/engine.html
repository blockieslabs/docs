The engine loop

A transaction is the unit of cost. Everything inside it should scale with what changed, not with the size of the World. Four places decide whether that is true.

The nine phases

A transaction is deliberately boring: it accepts inputs, applies them, stabilises derived values, and commits one new generation. The phases are ordered so that nothing observes a half-applied state.

PhaseWhat it doesWhat the cost scales with
acceptidentify the actor, the target, the inputone input
validatepayload shape, authority, revisionpayload size
stagerecord the intended changes without applying themwrite set
event phaserun reducers until the event queue is emptyevents delivered
process phasestep each ready run, at most onceruns stepped
value phasestabilise derived valuesdirty closure
preparecompute hashes, check invariantswrite set
commitbump the generation, make changes visiblewrite set
publishsend the generation to viewschanged entities × views

Two costs hide in that table. The value phase can accidentally scale with the whole graph instead of the dirty part. Commit and publish can accidentally scale with the whole document instead of the write set. Those are the two places a conforming engine becomes quadratic.

The value phase is where engines die

Derived values form a declared graph: a port's value is a function of its inputs. D-011 chose topological stabilisation with equality-gated propagation, and explicitly rejected runtime dependency tracking. That is the right trade for a serialisable World, but it puts all the pressure on how the graph is evaluated.

The naive version

The obvious stabiliser is a fixpoint loop. Visit every node; if anything changed, do it again.

repeat
  changed = false
  for node in all_nodes
    value = compute(node)
    if value != node.value
      node.value = value
      changed = true
until not changed

On a chain of G nodes, the first pass updates one node, the second updates the next, and so on. That is O(G²) visits. At ten thousand nodes it is tens of millions of computes, each with a deep equality check and possibly a sandbox call.

The version that scales

Four changes, in order of impact:

  1. Precompute a topological order. The graph is declared, so the order is a property of the document, not of the run. Store it as a flat array of integers. A transaction walks the array once, in cache order.
  2. Visit the dirty closure, not the graph. A changed input marks its transitive consumers. A bitset plus a worklist is enough. Most transactions touch a handful of nodes.
  3. Compare fingerprints before values. Give every value a cached canonical hash. Compare hashes first; only a hash match triggers a deep comparison. For interned values, pointer equality is the fast path.
  4. Cut off early. If a node's output fingerprint is unchanged, do not mark its consumers. On a stable graph this removes almost all of the work.
A correctness trap hiding in the optimisation

sum over floating-point values is not associative. If a fold is evaluated in parallel, or in a different member order, the result changes, and so does the World digest. BCS declares the fold operations but never fixes the reduction order. Until it does, a fast fold and a reproducible fold are not the same fold. The fix is a fixed order, usually member ID ascending with a fixed tree shape, or exact arithmetic for the numeric types that need it.

The fixed cost of a transaction

Every input opens a transaction. That is correct: a transaction is the unit of consistency. But the fixed cost is paid whether the payload is a database migration or a button press.

ComponentCost
Accept, validate envelope, authorise1–20 µs
Stage and journal1–50 µs, depending on copy strategy
Commit bookkeeping, generation bump1–10 µs
Persist (fsync)100–10,000 µs
Publish to V views10–1000 µs
Trace record1–10 µs

At a thousand inputs per second, a one-millisecond commit already consumes the whole second. The work inside the transaction might be ten microseconds. The architecture is paying a database transaction for a keystroke.

The fix is batching at the boundary, not inside the transaction. A3 collects inputs that arrive in a short window and opens one transaction. Semantics do not change: P-24 still says one step per run per transaction, and P-28 still drains the event queue before the process phase. Batching changes how many transactions carry the same events, not what a transaction means.

Two supporting changes make the batch cheap. Coalesce by target and port: two deliveries to the same event input keep their order in the queue but need one commit. Group commit: one fsync per batch, with the batch boundary in the log record.

Rollback is not a copy

If abort is implemented by cloning the World, a 10 MB document costs 10 MB per transaction. Use an undo journal: record the old value of each field before writing it, and replay in reverse on abort. For snapshots that must survive a commit, use a persistent map, so a new generation shares every untouched subtree. D-011 already asks for this; in practice it is a requirement, not an optimisation.

Steps are bounded, and that costs latency

Three rules compose into a latency multiplier:

  • A run steps at most once per transaction (P-24).
  • A step that returns neither an outcome nor a wait goes back to queued and steps again in a later transaction (P-22).
  • A dependency wait is satisfied by a value change visible only in the value phase, so the run is scheduled for a later transaction (P-33).

A program that needs K steps takes K transactions. A chain of K dependent runs takes K transactions and K publishes. At one millisecond per commit, a thousand-step program takes a second of wall clock even if each step is ten microseconds of work. A reactive pipeline of twenty stages has a twenty-frame lag at 60 Hz.

This is deliberate. Bounded steps give latency a ceiling and cancellation a clean point. The fix is not to remove the bound. The fix is to stop paying full commit and publish cost for each unit.

Call this a turn: several transactions back to back, one publish at the end. Each transaction still satisfies P-24 and P-34; the turn is a host-level grouping. It removes K−1 publishes, renders and network frames. It does not remove K−1 commits, so pair it with cheap commits.

Do not add a fast run kind

D-011 is explicit: there is no performance tier of process. Speed is an engine property. Adding a tier for speed forks semantics, and the tier becomes a second architecture with its own bugs.

Commit is not a save of everything

A commit produces a new generation. If producing it serialises the whole document, hashes the whole document, and sends the whole document to every view, then a session of T transactions is O(T × W). For a 10 MB World and a thousand transactions, that is 10 GB of serialisation. The cost is not the bytes; it is that the work is proportional to everything instead of to what changed.

Canonicalise per entity, not per document. A commit serialises only the entities in its write set. The document digest is a Merkle root over table chunks, so unchanged chunks reuse their hash. Chunk by table and by key range, typically 4–64 KB leaves. A save writes dirty leaves; a sync compares roots and descends only where they differ.

This is the same shape as Git's object model, and it fits C-11: one logical document, many physical chunks. The chunk is a storage detail. It must not become a place where occupancy or status is persisted.

Why canonical encoding is on the critical path

Without a canonical form, digest-pinned definitions cannot be produced reproducibly (PF-004), and two hosts cannot compare World digests (PF-072). The choice also fixes the cost: a form with sorted keys and a defined number form can be hashed incrementally. A form that depends on map iteration order cannot.

Check yourself

Why is a fixpoint loop quadratic on a chain?

Each pass visits every node but propagates a change only one step along the chain. A chain of length G needs G passes, each visiting G nodes, so G² visits. A topological order propagates the whole chain in one pass.

What does batching change, and what does it not change?

It changes how many transactions carry a set of inputs, and therefore how many commits, fsyncs, publishes and renders are paid. It does not change what a transaction means: one step per run, one coherent generation, the same ordering rules.

Why is a turn not a violation of P-24?

P-24 limits steps per run per transaction. A turn is several transactions, each still stepping a run at most once. The turn only groups the publishes, so views and renders see one generation instead of many.

Why can a parallel fold change the World digest?

Floating-point addition is not associative, so a different reduction order produces a different result. If the result is part of the document, the digest changes. A fixed reduction order or exact arithmetic keeps it reproducible.
