Scaling out

Beyond one process and one screen: sandboxes, sessions, views, disk, and the network. These are the costs that appear when the World has to leave memory.

The sandbox is a tax

A step runs in a JS or WASM adapter. The adapter is bounded and deterministic: no ambient time, randomness, network or filesystem (D-027). That isolation is the point, and it has a price. The boundary is crossed for every step, and the crossing costs far more than the work inside it.

OperationCost
Enter or leave a JS context0.1–1 µs
Create a fresh context1–50 ms
Parse and compile a module1–100 ms
Marshal a small object0.5–5 µs
Marshal a 1 MB buffer0.5–2 ms

A step with ten microseconds of actual work and three hundred microseconds of setup is 97% overhead. At ten thousand steps per second, that is three seconds of setup per second of work. The interpreter is the second problem: QuickJS or Boa is two to fifty times slower than a JIT on numeric code, which is why D-027 makes WASM the second adapter rather than an afterthought.

Five fixes, in order:

  1. One context per World, pooled per definition digest. Reset state between steps by restoring a heap snapshot or clearing a dedicated realm, not by destroying the isolate.
  2. Compile once per digest. The digest is the cache key. A definition that has been seen is a pointer lookup, not a parse.
  3. Batch the boundary. Pass a snapshot of all inputs for a batch of nodes, receive all outputs. A spreadsheet column becomes one call with typed arrays.
  4. Share memory with WASM. Values are offsets and lengths into one linear memory region, not copies. This is the difference between a microsecond and a millisecond for a large array.
  5. Use WASM for hot Blueprints. A Blueprint that runs on every cell or every frame is a SIMD kernel, not an interpreted function.
The constraint on all of it

A pooled context must not leak state between runs. The cheapest guarantee is structural: the step's input is the only way in, and the result is the only way out. If a step can read a global, the pool is a correctness bug waiting for a load spike.

Effects are I/O, not computation

An effect is an authorised external operation performed after commit (F-11). It is where the outside world gets in: an HTTP call, a file write, a message to another system. The latency is not yours to optimise; a network round trip is milliseconds to seconds.

The architecture already has the right shape: commit, then execute, then deliver the result as an event in a later transaction. The performance rules follow from it:

  • Never block the loop on an effect. Use an async outbox with a concurrency limit, not a synchronous call.
  • Batch completions. Ten effects finishing in the same window should be one transaction, not ten.
  • Keep an idempotency key per effect. At-least-once delivery is the contract; the key is what makes the retry safe.
  • Bound the dedup store. TTL plus compaction; an unbounded set of every effect ever executed is a memory leak with a correctness story.

Simulation must not become an event storm

A physics or 3D service is an effect-plus-derived-output provider. It may not write Blockie state directly; it publishes through a declared channel. That is the right rule, and it creates a temptation: publish every changed entity on every tick.

At 60 Hz with a thousand moving entities, that is sixty thousand events per second, each wanting a transaction. The fix is to decouple the simulation tick from the transaction rate:

  • Publish on change or on a threshold, not on every tick.
  • Coalesce samples per region or per entity.
  • Keep the tick fixed and deterministic; let the host decide when to commit.
  • Use a broadphase (BVH, grid, spatial hashing) so the simulation itself is not O(n²).

One index, many views

A view is a viewport plus a renderer plus a grant set. Views do not copy entities (D-007). That saves memory, but it creates a per-generation cost: each view has to decide what it can see.

If each view filters the World independently, the cost is V × N per generation. If each view also re-evaluates grants per entity, it is V × N × policy. If each view is serialised independently, it is V × N encodes. Ten views of ten thousand entities is a hundred thousand entity visits per frame, before drawing.

Build the index once per generation. Each view holds a bitset of visible entity handles, updated incrementally when the viewport or the World changes. Filtering is a bitwise AND, which is SIMD-friendly and O(N/64).

Grants compile the same way. A grant on a Composite covers its public aliases only (C-55). Precompute, per principal and scope, a bitset of permitted endpoints. A command check is a bit test, recomputed on policy or membership change rather than per command.

Redaction happens before publish

A renderer is never an enforcement point (C-57). If the host sends an entity to a view that may not read it, hiding it in the renderer is too late. The host must produce a per-view projection that omits it, once per generation, from the shared index.

Catch-up is the other half. A view that has not acknowledged generation N should not receive every intermediate delta. Give it a keyframe at N+k and let it resume. catching_up is the honest state; the fix is to make catching up cheap, not to pretend the view is current.

Durability is a log, not a document

If every commit fsyncs the document, throughput is capped by the disk: 100–1000 commits per second at best, often much less. If every commit writes the whole document, a session is quadratic in document size.

The write-ahead log is the durability boundary. Append a record per transaction, buffer records, and fsync once per batch or once per timer tick. A crash replays the log. Periodically write a chunked snapshot and truncate the log, so recovery does not replay a week of history.

The snapshot is chunked, so writing it is proportional to what changed since the last snapshot. The log and the archive compress well: entity records are highly repetitive, with the same keys and the same Blueprints, so zstd with a dictionary is a large win at low CPU cost.

Terminal runs are not hot

Occupancy only cares about non-terminal runs. But the registry retains every finished run for acknowledgement (F-22), and every scan pays for all of them. A long-lived World accumulates millions of finished runs while the hot set stays small.

Partition the registry by liveness: non-terminal runs in the hot table, terminal and acknowledged runs in a cold archive. The registry is still authoritative, and identity still survives (C-9, C-10); it is just partitioned. A host → active run index makes the hot path constant time.

Sync is a Merkle walk

Multi-client sync is deferred (F-20), but the shape follows from the commit design. If the document is a Merkle tree of chunks, two hosts compare roots and descend only where they differ. Each entity carries a version vector, so a conflict is detectable without shipping the World.

What does not work is broadcasting full state per edit: it is O(W) per change and it gets worse as the World grows. Delta sync, keyframes and interest-based replication are the only shapes that survive a large World.

Check yourself

Why is creating a JS context per step so much worse than it sounds?

Because it is milliseconds against microseconds. A step with ten microseconds of work and a millisecond of setup is 99% setup. Pooling the context moves the cost to once per definition, not once per step.

Why does a per-view filter not need a copy of the World?

The view holds a bitset of visible handles, not entities. The shared generation is immutable; the bitset selects from it. Memory scales with the number of entities, not with entities times views.

Why is a WAL faster than writing the document?

The log record is proportional to the change, and the fsync can be shared across a batch. The document write is proportional to the World and cannot be shared without a snapshot strategy.

Why can a renderer not be the place that hides a restricted entity?

Because by then the entity has already been sent. C-57 makes the renderer a presentation layer, not an enforcement point; the host must omit the entity before publishing the view.
