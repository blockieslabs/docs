Blockies, explained

Blockies is a visual world made of small, fixed-shape pieces that AI agents arrange and operate. The pieces are deliberately limited. The arrangements are not.

This guide teaches the architecture from the ground up. Every term is defined where it first appears and again in the glossary. If you only read one page, read this one.

The thirty-second version

  1. One kind of inhabitant. A Blockie is a small entity with a fixed visual shape, an identity, some state, and typed ports. It never changes into a different shape to mean something else.
  2. Shape comes from composition. Bigger, more expressive things are built by grouping Blockies — never by inventing new primitives at runtime.
  3. Activity is a separate thing. A Run is a long-lived, pausable activity. It lives inside a Blockie, which represents it.
  4. Grouping is not a Blockie. A Composite is an assembly with membership, an optional manager, and a public face. It has no shape of its own.
  5. Relationships never imply each other. Being near something, belonging to something, controlling something, and observing something are four different facts.

What problem is this solving?

An AI agent is good at arranging things and bad at inventing a consistent visual language on the fly. If every agent could invent its own shapes, two Worlds would never look like they came from the same system, and nothing would be reusable.

So the vocabulary is fixed and versioned. Agents get expression from arrangement, grouping, and behaviour — not from new primitives. That trade is the whole design.

The central principle

A small, deliberately designed vocabulary of Blueprints; complex and expressive visualizations emerge through composition and interaction.

The cast of characters

ThingWhat it isWhat it is not
Blockie A persistent inhabitant: identity, one Blueprint, config, state, optional placement. Not a program, not a mode, not a container.
Composite An explicit assembly of Blockies and nested Composites. Not a Blockie, not a Blueprint, has no ports of its own.
Run A managed activity: resumable, cancellable, observable. Not a thread, not a Blockie, not a function call.
Blueprint An immutable plan: appearance, ports, schemas, optional logic. Not an instance, not mutable, not a Composite.

The one rule that explains most of the design

These are separate facts. The architecture spends most of its effort keeping them separate, because collapsing any two of them produces a system that looks fine in a demo and breaks when agents operate it.

Status

This is a working design, not a frozen specification. The model is complete enough to implement against, and every decision is recorded. Three things are still unwritten: the effects protocol, the canonical encoding used for digests, and an ontology glossary in the repo (this guide's glossary is the closest thing). Where the old v0.1 documents disagree with this guide, this guide is current.
