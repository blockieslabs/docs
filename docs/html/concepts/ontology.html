Blockies / Concepts

Entities and identity

A World contains four kinds of thing. Everything else in the architecture is a relationship between them, a property of them, or a value derived from them.

What an entity is

An entity is something that exists in its own right: it has an identity, it can be referred to, and it survives changes around it. In Blockies there are exactly four, and no more.

EntityExists toOwns
Blockie Be an inhabitant of the World. Its identity, one Type, configuration, state.
Composite Be an explicit assembly of other entities. Membership edges, aliases, folds, optional manager, optional presentation.
Run Be a long-lived, pausable activity. Its own state, inbox, status, optional dispatch grant.
Definitions Be immutable blueprints. Nothing at runtime. They are pinned references.
Two definitions, not one

A Type package is a blueprint for a Blockie: its shape, ports, schemas, and optional logic. A process definition is a blueprint for a Run: what it claims, what it publishes, and how it steps. They are different artifacts with different jobs, which is why they are not two kinds of one thing.

Identity

Every entity has an opaque identifier. "Opaque" means the system never looks inside it: it is a string, and its only job is to be stable.

Identity rules

  • Stable for the life of the entity, unique inside the World.
  • Never derived from position, display name, template path, membership, or parentage.
  • Survives movement, regrouping, and every activity the entity has ever hosted.
  • Never reused after deletion or dissolution.

Why so strict? Because almost every other guarantee depends on it. If an ID changed when a Blockie moved into a Composite, every connection, every run, and every undo record would break. If an ID were derived from a position, two agents editing the same World would disagree about what they were editing.

A Blockie, precisely

A Blockie has four fields. That is the entire entity.

Blockie {
  id      an opaque identifier
  type    a pinned Type package reference
  config  typed configuration
  state   typed Model State
}

Notice what is not there. No placement (it lives in its own table). No mode. No parent. No owner. No "is it running" flag. Each of those is either a separate record or a value computed from records that already exist.

The mode question

Older drafts said a Blockie is in "drawing mode" or "computing mode". That is now derived, and the words are retired.

A Blockie is occupied if the run registry holds an activity for it that has not finished. Otherwise it is vacant. There is no field to get out of sync, because there is no field.

The processes page explains why "computing" was the wrong word: a run that is queued or paused is not computing anything, yet it is still attached.

Why there is no "Computer Blockie"

An earlier design had Computer and Drawing Blockies as two primitive Types. It failed for a reason worth internalising: hosting an activity is not a kind of thing, it is a relationship a thing can be in. If you make it a Type, then a Blockie must change Type to start work, which breaks identity, breaks its ports, and makes "what can this Blockie become" a question with no answer.

The replacement is a rule: a Blockie's Type is stable, and it may host a Run subject to its Type's declared permissions. The types page covers those permissions.

Terms on this page

  • Entity — a thing with identity that exists in its own right.
  • Opaque identifier — a string the system never parses or derives.
  • Pinned definition — a reference to one exact version and content digest, so behaviour cannot change under you.
  • Derived value — a value computed from stored records, never stored itself.
  • Occupancy — whether a Blockie currently hosts an unfinished Run.

Check yourself

Why does a Blockie have no "is running" field?

Because the run registry already knows. Two records of the same fact will eventually disagree, and then nothing can decide which is true. One authority, everything else derived.

A Blockie moves from one Composite to another. What changes?

Its membership edge and its placement scope. Not its ID, Type, state, ports, or any run it hosts.

Why can't an ID be derived from a template path?

Because templates get edited and renamed. An ID derived from a path would change when the template changed, which would break every reference to the instance.
