Blockies / Concepts

Relationships and authority

If you remember one page of this guide, make it this one. Almost every design argument in Blockies is about keeping two relationships from being confused for each other.

The same Blockie, eight different facts

Two entities can be related in several ways at once, and each way answers a different question. None of them implies another.

Concrete confusions this prevents

"It's next to the group, so it's part of it"

No. Membership is an explicit edge. Proximity is placement, and placement is semantically inert.

"It spawned the worker, so the worker is in its group"

No. Parentage is a fact about activity. Membership is a fact about assembly. The child's host Blockie can be placed anywhere, or nowhere.

"It's the manager, so it can read the members' state"

No. Management grants dispatch and nothing else. The manager sees what its own ports are wired to.

"It's watching, so it can act"

No. Attention is derived from what a session frames and what a Run's inputs are wired to. It grants nothing.

Attention is derived

Attention answers "what is being watched", and it is not an entity. It is a projection over two sources:

  • an external actor attends to whatever its session frames and is granted;
  • an in-world Run attends to the entities whose outputs its host's inputs are connected to.

Because it is derived, there is no second truth about who is working on what. And because it grants nothing, moving a Blockie next to a Composite changes exactly one thing: the picture.

Authority

Authority answers "who may act". It is split in two, and the split matters:

HalfLives inWhy there
Roles and grantsthe World documenta World must carry its own rules to be portable
Principals and bindingsthe host sessionidentities are deployment-specific

Four verbs

VerbAllows
deliversubmit an event to an endpoint
readread values and subscribe to generations
mutatedocument operations: create, move, group, connect, present
runattach, cancel, suspend, resume

Scopes are world, entities, or endpoints. A grant on a Composite covers its public aliases only — never a member port, never member state. Nothing is granted by default.

Checked once, at the boundary

Authority is checked when an event or command enters the World. Internal routing — alias resolution, forwarding, dispatch — is authorised by structure, not re-checked against the actor.

Why

If every hop re-checked, a manager could never dispatch to a worker: the original voter would need permission on the worker's input. And authority that depends on route shape cannot be audited.

The file holder

Whoever opens a World owns it: the owner has implicit mutate and run. Policy governs sessions, not the person holding the file. A file holder can edit the document, including its policy — pretending otherwise would be theatre.

Lifecycle authority is its own thing

Being able to stop a Run is not management, and not membership. A parent Run may ask its descendants to cancel; a host may cancel its own Run; World policy may allow an operator to suspend anything. None of those make anyone a manager.

Terms on this page

  • Attention — a derived projection of what is being watched.
  • Authority — a grant that permits an action on a scope.
  • Grant — verb plus scope, held by a role or a Run.
  • Principal — the acting identity a host issues to a session.
  • Lifecycle authority — the separate right to stop an activity.

Check yourself

An agent moves its Blockie into a Composite. Did it gain authority?

No. Membership is not authority. Its grants are unchanged, and it still cannot read member state.

Who can cancel a worker Run inside a Composite?

Whoever holds run on it, its parent Run, or its host's owner. Not necessarily the Composite's manager.

Why does a manager's dispatch not re-check the original voter's permission?

Because the manager's right to dispatch was authorised once, at designation. Re-checking per hop would make delegation impossible and audit meaningless.
